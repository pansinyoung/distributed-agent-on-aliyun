# 决策 01 · 部署工具：Serverless Devs vs aliyun CLI

> 用途：M1 第一个决策。决定 `npm run ship` 这条回路怎么写。
> 数据来源：本机实测（2026-10-29）+ 阿里云官方文档 + GitHub API。凡标「实测」的都是在你这台机器上跑出来的，不是转述。

---

## 0. 结论

**不是二选一，是按职责分工。但当前 `s` 在你机器上不可用，且这是一个必须先修的环境问题。**

| 职责 | 建议工具 | 理由 |
|---|---|---|
| 打包 → 上传 OSS → 创建/更新函数 → 绑触发器 | **`s deploy`**（fc3 组件） | aliyun CLI 没有编排能力，这段要自己写 |
| 构建钩子（`tsc` / `esbuild` / `npm install`） | **`s` 的 `pre-deploy`** | aliyun CLI 完全无此概念 |
| 验收断言、读函数状态、取日志、开会话 | **`aliyun fc`** | 纯 CLI、无 daemon、可在脚本里断言退出码 |
| 断点排查、精细控制 | **`aliyun fc`** | 每一步是原子 API，看得见 |

**三条硬结论：**

1. 🔴 **`s` 当前不可用**：`s -v` 60 秒无任何输出（已排除沙箱因素，脱离沙箱仍卡）。根因是 `~/.s` 归属 `root`，当前用户不可写。
2. 🟡 **`aliyun fc` 可用但不会帮你部署**：它是 OpenAPI 封装，没有 `deploy` 命令。`create-function` 要求 `--code` 指向 **OSS 对象**，即打包上传得自己实现。
3. 🔴 **一个和工具无关的平台约束**：FC 3.0 内置 Node.js 运行时最高 `nodejs20`，而 Node 20 **没有原生 TS 支持**。这意味着必须有编译步骤——这条把 `s` 的 `pre-deploy` 价值显著抬高。

---

## 1. 两者到底是什么关系

先把定位说清，否则对比会失真。

| | Serverless Devs (`s`) | aliyun CLI |
|---|---|---|
| 本质 | **部署工具链**（声明式编排） | **OpenAPI 通用客户端**（原子调用） |
| 抽象层次 | 应用/资源级（`s.yaml` 描述整个应用） | API 级（一次调用一个 action） |
| 有状态 | 有（daemon + 本地组件缓存 + 状态 diff） | 无状态 |
| 谁来编排 | 工具 | 你自己 |
| 典型命令 | `s deploy`（一条命令完成十几步） | `aliyun fc create-function`（一步） |
| 归属 | 开源项目（Serverless-Devs），阿里云官方文档收录 | 阿里云官方 CLI |

**一句话**：`s` 帮你把「部署一个应用」拆好的十几步自动跑完；`aliyun` CLI 只提供每一步的原子操作，串起来是你的事。

它们**不是竞品**，是两个层次。真正的竞品关系是 `s` 的 fc3 组件 vs 你自己写的 `ship` 脚本。

## 2. 本机实测数据

### 2.1 可用性

| 项 | Serverless Devs | aliyun CLI |
|---|---|---|
| 版本 | `@serverless-devs/s` **3.1.10** | **3.3.2** |
| 安装位置 | `~/.nvm/.../node_modules/@serverless-devs/s`（全局，**root 所有**） | `/usr/local/bin/aliyun` |
| `-v` / `--help` | 🔴 **60 秒无输出、无网络连接、不退出** | ✅ 立即返回 |
| 账号配置 | ❌ 无。`~/.s/config/` 只有模板文件 | ⚠️ 有 `default` profile（cn-beijing），但 **AK 已失效** |
| FC 能力 | fc3 组件，**首次使用需联网下载** | `aliyun-cli-fc` 插件**已装**，60+ 命令 |

### 2.2 `s` 卡住的定位过程

| 步骤 | 观测 | 结论 |
|---|---|---|
| `s -v`（前台） | 60 秒无输出 | 挂起 |
| 接 `stdin=/dev/null` | 25 秒仍无输出 | 不是等输入 |
| `lsof -p <pid> -a -i` | **无任何网络连接** | 不是联网卡住 |
| `lsof -p <pid>` | 只打开 node 二进制，**未加载 `lib/` 下任何 JS** | 卡在极早期 |
| `node -e "require('.../lib')"` | **`B:loaded 155 ms`**，但进程不退出 | 加载很快，**卡在事件循环** |
| 脱离沙箱重跑 | 30 秒仍无输出 | **排除 WorkBuddy 沙箱** |
| `ls -ld ~/.s` | `drwxr-xr-x 4 root staff` | 🔴 **root 所有** |
| `touch ~/.s/_wtest` | `EACCES: permission denied` | 🔴 **当前用户不可写** |

**根因判断**：`s` 装的时候用了 `sudo npm i -g`，导致 `~/.s`（配置/日志/组件缓存目录）归 root。`s` 启动时需要读写该目录，失败后卡在事件循环里且不输出错误——**静默挂起，这是最坏的失败方式**。

`lib/daemon/lib.js`（1.5 MB）的存在说明 `s` 采用 daemon 架构：CLI 与常驻进程通信以加速组件加载。这解释了两件事：加载 155ms 完成但进程不退，以及 `ps` 里看不到残留 daemon（从未成功启动过）。

### 2.3 `aliyun fc` 的能力边界（实测 `--help`）

FC 3.0 插件已装，60+ 命令，关键几条：

| 命令 | 说明 |
|---|---|
| `create-function` | 建函数。`--code` 需指向 **OSS 对象**（`ossBucketName` + `ossObjectName`）或 `zipFile` |
| `update-function` | 改函数。**`--timeout` 最大 86400 秒** |
| `invoke-function` | 同步调用 |
| `get-function-code` | 取代码包详情 |
| `create-session` / `get-session` / `list-sessions` / `delete-session` | **显式会话管理**，支持 `HEADER_FIELD` / `GENERATED_COOKIE` 亲和 |
| ❌ `deploy` | **不存在**。打包、上传 OSS、等待就绪、绑触发器，全部要自己写 |

### 2.4 一个意外收获

之前阿里云方案调研里列过 10 个「未经验证项」，其中两条靠这次实测直接得到答案：

- **#1「会话亲和是否需要 AgentRun 层支持」** → 不需要。`sessionAffinity` 是 FC 3.0 `CreateFunction`/`UpdateFunction` 的**标准参数**（取值 `MCP_SSE` / `GENERATED_COOKIE` / `HEADER_FIELD` / `NONE`），`aliyun fc` 可直接设置。
- **#2「执行时长上限」** → API 层面 **86400 秒**（24 小时）。真实 HTTP 请求是否有更短上限，属 M1 第 5 步待实测项。

## 3. 能力矩阵：按 M1 实际要做的动作逐条对比

不用泛泛的功能表，只比 M1 到 M3 会真正用到的动作。

| M1–M3 需要的动作 | `s deploy`（fc3） | `aliyun fc` | 差异性质 |
|---|---|---|---|
| 打包代码（zip） | ✅ 自动 | ❌ 自己 `zip` | 工作量 |
| 上传代码包到 OSS | ✅ 自动 | ❌ 自己 `aliyun oss cp` | 工作量 |
| create 还是 update（幂等） | ✅ 自动按状态判断 | ❌ 自己查再分支 | 工作量 |
| 构建（`tsc` / `esbuild` / `npm install`） | ✅ `pre-deploy` 钩子 | ❌ 无此概念 | **能力缺失** |
| 本地模拟线上 runtime 构建 | ✅ `s build --use-sandbox` | ❌ | **能力缺失** |
| 等待函数就绪 | ✅ 自动轮询 | ❌ 自己轮询 `get-function` | 工作量 |
| 触发器 / 自定义域名声明式编排 | ✅ `s.yaml` 描述 | ❌ 逐 API | 工作量 |
| 部署结果 diff（改了什么） | ✅ 有计划预览 | ❌ 无 | 便利性 |
| 设 `sessionAffinity`（M2+ 关键） | ✅ 透传 | ✅ 直接参数 | 平手 |
| 精确控制每一步、可断言 | ❌ 被封装 | ✅ **原子 API** | **可测性** |
| 在脚本里判断成功/失败 | ⚠️ 靠 daemon 返回码 | ✅ 靠退出码 | 可靠性 |
| 无守护进程、纯调用 | ❌ 有 daemon | ✅ | 可靠性 |
| 调用函数、取日志 | ✅ `s invoke` / `s logs` | ⚠️ 需装 SLS 插件 | 便利性 |
| 与 CI 集成 | ⚠️ 有方案，但 daemon 是隐患 | ✅ 纯 CLI | 可靠性 |

**读法**：`s` 的独占优势全在**「部署前」和「编排」**；`aliyun fc` 的独占优势全在**「部署后」和「可控」**。没有一方覆盖另一方。

### 3.1 唯一真正无法替代的一项

**构建钩子**。这是 `s` 唯一「aliyun CLI 无论怎么写都补不上」的能力——不是难写，是 `aliyun` CLI 里根本没有「部署前先跑一条命令」这个概念。

考虑到第 4 节的 Node 运行时约束，这一项在 M1 就是必需的，不是可选的。

## 4. 平台层共同约束（与选哪个工具无关，但会反过来影响选型）

这几条无论用 `s` 还是 `aliyun` CLI 都一样，但**它们直接决定了构建步骤是否必需**。

### 4.1 🔴 Node.js 运行时只到 20（内置）

FC 3.0 内置 Node.js 运行时：`nodejs12 / 14 / 16 / 18 / 20`，**最高 `nodejs20`**（Debian 10）。

这是一条硬约束，因为它和我们本地方案冲突：

| 环境 | Node | 能直接跑 `.ts` 吗 |
|---|---|---|
| 你本机 | 24.14.0 | ✅ 原生 type stripping |
| FC 内置 `nodejs20` | 20.x | ❌ **Node 20 完全没有原生 TS 支持** |

**所以「零构建、零依赖，本机怎么写就怎么跑」这个前提在 FC 上不成立。** 必须有一步编译。

三条绕过路径：

| 路径 | Node 版本 | 能否跑 `.ts` | 代价 |
|---|---|---|---|
| **A. `nodejs20` + 预编译** | 20 | ❌ 先 `tsc`/`esbuild` 出 `.js` | 多一步构建；但最简单 |
| **B. `custom.debian12` 自定义运行时** | 22 / 20 / 18 | ⚠️ Node 22.6+ 需 `--experimental-strip-types` | 要自己写 HTTP server + 启动命令 |
| **C. `custom-container`** | 任意（含 24） | ✅ 原生 | 要 Docker + ACR 镜像仓库 |

> 这三条是本机 Node 24 与云端 Node 20 的落差造成的，不是阿里云的缺陷——它是「函数运行时按发行版打包」的普遍现象（AWS Lambda 同理）。

**对选型的影响**：路径 A 需要构建钩子 → `s` 的 `pre-deploy` 直接可用，`aliyun fc` 要自己在 `ship` 脚本里插一步。
路径 C 需要 `docker build` + `docker push` → `s` 也是唯一原生支持的（`s build --dockerfile` + 自动推 ACR）。

### 4.2 其余平台事实（已确认）

| 项 | 值 | 来源 |
|---|---|---|
| 函数 `timeout` 上限 | **86400 秒** | `update-function --timeout` |
| `sessionAffinity` 取值 | `MCP_SSE` / `GENERATED_COOKIE` / `HEADER_FIELD` / `NONE` | `create-function` API |
| SSE 流式是否支持 | ⚠️ **未验证**。这是 M1 第 5 步的核心待测项 | — |
| 部署形态（Web 函数 vs 事件函数） | ⚠️ **未验证**。决定 handler 写法 | — |

## 6. 三条可选路径

### 路径 A：修好 `s`，用它做部署编排（推荐）

```sh
# 1. 修正权限（安装时用了 sudo 导致的）
sudo chown -R "$(whoami)" ~/.s

# 2. 验证
s -v          # 应输出 3.1.10，且 1 秒内返回

# 3. 配账号（如仍不可用，重装一次且不要 sudo）
npm uninstall -g @serverless-devs/s
npm install -g @serverless-devs/s
s config add
```

| 优点 | 缺点 |
|---|---|
| `pre-deploy` 解决构建问题（第 4.1 节的必需步骤） | 依赖 daemon，出问题会静默挂起 |
| 自动打包上传 OSS，`ship` 脚本只需 3 行 | `~/.s` 权限问题修不好就完全不可用 |
| 幂等、diff、触发器编排全自动 | 17 个月未发版，长期有风险 |
| `s build --use-sandbox` 本地模拟线上构建 | 卡住时无任何错误输出，排查成本高 |

**如果修好，M1 的 `ship` 就是**：`s deploy -y` + `curl` 冒烟 + `aliyun fc` 断言。

### 路径 B：纯 `aliyun fc` + 自写 `ship` 脚本

| 优点 | 缺点 |
|---|---|
| 无 daemon，每步可控、可断言、可计时 | 打包/上传/幂等/轮询全部自己写（约 100–150 行） |
| 官方 CLI，维护确定性强 | **无构建钩子**，构建要自己串 |
| 失败有明确退出码和错误信息 | 触发器、域名等多资源场景会变繁琐 |

**M1 的 `ship` 会长这样**：
```
esbuild 打包 → zip → aliyun oss cp → 
查函数是否存在 → create 或 update → 轮询 get-function 就绪 → curl 冒烟
```

工作量可控，且每一步都能测——**这在对「部署回路 30 秒」有要求的阶段反而是优势**，因为你能精确知道时间花在哪一步。

### 路径 C：混合

`s deploy` 负责编排，`aliyun fc` 负责验收断言与状态查询。**这是 §0 结论里的分工方案，只有路径 A 修好后才成立。**

---

## 7. 建议

**先花 10 分钟试路径 A。** 理由不是「s 更好」，而是：

1. **构建钩子是刚需**（第 4.1 节），`s` 是唯一原生提供它的
2. 修权限只需要一条 `chown`，成本极低
3. 如果修好后仍然卡（说明是 daemon 与新环境的其他冲突），就立刻转路径 B，损失 10 分钟

**判定标准（不凭感觉）**：
- `s -v` 在 1 秒内返回 → 走路径 A
- 仍然挂起 → 走路径 B，不要再纠缠

**路径 B 是不可耻的退路**：M1 只有一个函数、一个端点，自写 100 行脚本的代价远小于长期忍受一个会静默挂起的 daemon。而且自写的过程会让你真正理解「部署一个函数」拆开是什么——这本身就在你的学习目标里。
